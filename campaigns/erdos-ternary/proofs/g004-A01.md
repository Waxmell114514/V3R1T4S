# g004-A01: ablation of the g003-L01 per-node speedup

Measurement experiment. No theorem, no new Lean result. Every number below is copied from command output
(benchmark log, 2026-11-24 16:09:41 to 16:20:59 UTC). Reason for the experiment: reports/gen_003/critic_L01.md
("ablate before attributing").

## Mechanisms

On top of the g002-L01 baseline (`Checker.explore`: per node, `N < r`, own trit by `Nat.powMod 2 r (3^(i+1))`,
single-member `r ≤ 8` leaf, else three child calls):

* **(a) child pre-test**: the parent tests each child's trit (and `N < r'`) before the recursive call, so a
  child that ends on its trit costs no call. Without (c) the child trit is a `Nat.powMod 2 r' (3^(i+2))`.
* **(b) scan**: a single-member class (`N < r + 2*3^i`, `r > 8`) is finished by reading the remaining trits of
  `2^r mod 3^L` one by one instead of building three children per level. Without (c), `2^r mod 3^L` is one
  `Nat.powMod 2 r (3^L)` at the first single-member node.
* **(c) table + incremental state**: each node carries `v = 2^r mod 3^L`, children get `v * g mod 3^L` with
  `g = 2^(2*3^j) mod 3^L` from a per-level table; no `Nat.powMod` per node.

`L = 40` (as `CheckerShard.modExp`); levels `>= L` fall back to the baseline (never reached at these N).
No sharding in any variant (one shard). Eight variants: `off`, `a`, `b`, `c`, `ab`, `ac`, `bc`, `abc`
(`abc` is a copy of `CheckerShard.fast` started at level 0). Two references call the committed code directly:
`ref_g002 = Checker.check N`, `ref_g003 = CheckerShard.checkShard N 0 1`.

## Method

* Code: `lean/.scratch/Ablate.lean` (untracked, sha256 `ec1b400b3b366bc327d033fbe09a50a2e81406c059c35b34f478fc99669c1474`),
  importing the built `ErdosTernary.CheckerShard` (commit 770152b, checker files unchanged). Computation only,
  no proofs.
* One process per run: `BV=<variant> BN=<k> nice -n 10 lake env lean .scratch/Ablate.lean`, `LEAN_NUM_THREADS=1`,
  one benchmark process at a time. The `#eval` reads `N = 2 * 3^k` from the environment (so nothing is
  constant-folded at elaboration) and times the evaluation with `IO.monoNanosNow` (`eval_s`). It runs in the Lean
  IR interpreter, the same path `native_decide` uses for the committed shards.
* Process wall time was also recorded. `BV=none` runs (imports and elaboration only) give the import time:
  1.730 s ± 0.119 (k = 20), 1.734 s ± 0.106 (k = 22). "wall − import" subtracts the import run of the same
  repeat.
* 3 repeats, round-robin (rep → k → variant), so drift hits every variant equally. Load average 1.5 to 2.1
  during the runs (other agents). Lean 4.36.0, Intel Xeon @ 2.30 GHz, 4 cores.
* Every run returned `result=true`.
* mean ± sample std over 3 runs. Speedup = mean(off) / mean(variant).

## Reading (HEURISTIC where it explains, not measured)

* **(b) scan is the main mechanism**: 1.75x alone. This fits the tree shape above, where about 75 % of calls
  sit in single-member tails.
* **(b) and (c) interact strongly**: bc = 2.94 to 3.03x, more than the product 1.76 × 1.19 ≈ 2.1. Likely
  reason (not measured): in `b` alone each single-member tail starts with one `Nat.powMod 2 r (3^40)`, a
  large-exponent powMod, while with (c) `v` is already at hand and the tail costs only the digit reads.
* **(a) adds little once (b) and (c) are on**: abc / bc = 1.03x at k = 22, and at k = 20 the two are equal
  within noise (1.939 ± 0.102 vs 1.920 ± 0.040). Alone (a) gives 1.18 to 1.20x, because without (b) it mostly
  saves calls on `N < r` leaves and trit leaves.
* **(c) alone helps (1.19 to 1.25x)**. This corrects the g003 ledger line "增量状态本身无效" only in part: the
  g003 implementer's "incremental state alone" was not this exact variant, so the two need not conflict. Here
  (c) includes the table.
* Corrected attribution for the ledger: the g003 gain is about (b)·(c) jointly (≈ 3.0x). (a) is ≤ 1.03x on top.

## What to try next for speed (untested suggestions)

1. **Keep all of `v` in a machine word.** `3^40 = 12157665459056928801 > 2^63`, so `v`, `g` and `v * g` are
   GMP bignums (Lean `Nat` is unboxed only below 2^63). With modulus `3^L < 2^32` (L ≤ 20) the products fit,
   but the table then runs out before the tree's depth (~k + 1 levels). Options: two-limb residue arithmetic in
   `UInt64`, or re-seeding `v` with one powMod at level 20.
2. **Scan the tail without the table list**: (b) is where the time goes. Reading trits of `v` is a chain of
   `/ 3`. Testing one 3^m block of trits at a time could cut that chain.
3. **Compiled rather than interpreted evaluation** (`precompileModules` or a compiled helper). All numbers here
   are from the IR interpreter. This changes the trust story (still tier B) and must be checked with the
   auditor first.
4. Drop (a) from future designs if it costs proof complexity: it buys ≤ 3 % once (b)+(c) are in.

## Caveats

* The interpreter's cost model is not compiled code. Ratios may differ under compilation.
* There are 3 repeats on a shared machine (load ~2). Differences under ~5 % (abc vs bc, ref vs copy) are
  within noise.
* Scratch files are untracked (as instructed). The hashes above identify the code that produced the numbers.
