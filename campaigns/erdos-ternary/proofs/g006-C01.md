# g006-C01: two-word checker state (one mechanism: `2^r mod 3^76` in two scalar words, table to level 74)

Prediction recorded before running (orchestrator, from critic_C02): <= 60 ns/unit; `UpTo (2*3^34)` tier B in
<= 45 min CPU; growth <= 4.1x per two powers of 3.
Outcome: 45.4-45.7 ns/unit, flat from K = 24 to K = 34 (met). `UpTo (2*3^34)` took 1572 s CPU = 26.2 min (met).
Growth was 4.00x per two powers for K = 24..32, and 4.03x for 32 -> 34, where per-module import overhead is included (met).
`UpTo (2*3^36)` is LEAN-VERIFIED tier B: 6260 s CPU (16 shards, 45.5 ns/unit, 3.98x over 2*3^34), about 38 min wall with 3 at a time.
New finding: for K >= 40 (N > 2^63) the class representative `r` and `N` themselves are bignums. A sampled
shard ran 9.9x slower at K = 40 than at K = 38, where 4x was expected (see "Scaling").

## Change
* `lean/ErdosTernary/Native/ETNative.lean`, new namespace `ErdosTernary.CheckerWord2`. It is Mathlib-free and
  precompiled, with no attributes, `extern`, `implemented_by`, `unsafe` or `partial`. It defines `mulLo`,
  `mulHi`, `Lv2`, `scanH`, `scanL`, `fastH`, `fastL`, `entry`, `tableL`, `tableH`, `top` and `checkWord2`.
  Existing definitions are unchanged. It reuses `Checker.explore`, `CheckerWord.scanT` and `CheckerWord.wordDepth` (= 10).
* State: `lo = 2^r % 3^38` and `hi = 2^r % 3^76 / 3^38`, both `< 3^38 < 2^63`. Table entry `j` stores
  `g = 2^(2*3^j) % 3^76` as four base-`B` pieces (`B = 3^19 = 1162261467`, a literal):
  `g = g0 + B g1 + B^2 h0 + B^3 h1`.
* `mulLo lo g0 g1` and `mulHi lo hi g0 g1 h0 h1` do a schoolbook product mod `B^4 = 3^76` with carries. The inputs
  are split as `a0 = lo % B`, `a1 = lo / B`, `c0 = hi % B`, `c1 = hi / B`. The columns are
  `t0 = a0 g0`, `t1 = a1 g0 + a0 g1 + t0/B`, `t2 = a1 g1 + a0 h0 + c0 g0 + t1/B` and
  `t3 = a0 h1 + a1 h0 + c0 g1 + c1 g0 + t2/B`. The new low word is `t1%B * B + t0%B` and the new high word is
  `t3%B * B + t2%B`.
  * For in-range inputs, every partial product is `< 3^38` and every column is `< 4*3^38 + 4*3^19 < 2^63`. So every
    value is a scalar `Nat`: no GMP and no allocation in the hot loop.
  * `mulHi` recomputes `t0` and `t1` (13 products per child instead of 10), because without attributes the two
    words cannot share one inlined body, and returning a pair would allocate.
* Tables: `tableL 10 27` covers levels 10..36, where the child trit `j+1 <= 37` is read from `lo` with
  `q = 3^(j+1)`. `tableH 37 38` covers levels 37..74, where trits 38..75 are read from `hi` with `q = 3^(j+1-38)`.
  `fastL` runs into `fastH` at level 37.
* Single-member tails:
  * `scanL` reads the remaining `lo` trits, then `CheckerWord.scanT` reads the 38 trits of `hi`.
  * `scanH` reads the remaining `hi` trits.
  * Both then fall back to `Checker.explore` at level 76.
  * No `Nat.powMod` runs below the shard level, except the one `Nat.powMod 2 r (3^76)` per shard-level node in `top`.
* Fallbacks are kept and sound. A node that still has several members at level 75 goes to `explore N F 75 r`; this
  cannot happen for N < 2*3^75. A tail past trit 75 goes to `explore` at 76.
* `lean/ErdosTernary/CheckerWord2.lean` holds the proofs and is imported from `lean/ErdosTernary.lean`. It adds
  `import Mathlib.Tactic.LinearCombination`.
* Records, not imported by default:
  * `Records/UpTo34.lean` + `Records/UpTo34/Shard{0..7}.lean`: `checkWord2 (2*3^34) s 8 = true` by native_decide.
  * `Records/UpTo36.lean` + `Records/UpTo36/Shard{0..15}.lean`: `checkWord2 (2*3^36) s 16`.
* `Records/README.md`: new rows and the trust sentence.

## Theorems
* `CheckerWord2.mul2_gen (B lo hi g0 g1 h0 h1) (hB : 0 < B)`:
  `mulLoB B lo g0 g1 + B*B * mulHiB B … = (lo + B*B*hi) * (g0 + B g1 + B*B h0 + B*B*B h1) % (B*B*(B*B))`
  and `mulLoB B lo g0 g1 < B*B`.
  * It holds for all inputs. Only speed depends on the bounds. The proof generalizes the four digit/carry pairs and
    uses `linear_combination` over ℤ.
  * `mulLo_eq`/`mulHi_eq : mulLo … = mulLoB 1162261467 …` hold by `rfl`.
* `CheckerWord2.st_step`: `St r lo hi → EG i e → St (r + 2*3^i) (mulLo lo e.g0 e.g1) (mulHi lo hi …)`.
  The state invariant is `St r lo hi := lo = 2^r % 3^38 ∧ hi = 2^r % 3^76 / 3^38`.
* `CheckerWord2.checkWord2_sound {N m : ℕ} (hm : 0 < m) (h : ∀ s < m, checkWord2 N s m = true) : UpTo N`.
  Tier A. `python3 verify/lean_audit.py ErdosTernary.CheckerWord2 ErdosTernary.CheckerWord2.checkWord2_sound`
  gives `LEAN_AUDIT: PASS tier=A axioms=['Classical.choice', 'Quot.sound', 'propext']`.
* `upTo_34 : UpTo (2 * 3 ^ 34)`. Tier B. `lean_audit.py ErdosTernary.Records.UpTo34 ErdosTernary.upTo_34 --expect UpTo:2*3^34`
  gives `LEAN_AUDIT: PASS tier=B`. The axioms are propext, Classical.choice, Quot.sound and
  `CheckerWord2.word2_34_{0..7}._native.native_decide.ax_1_1`.
* `upTo_36 : UpTo (2 * 3 ^ 36)`. Tier B. `lean_audit.py ErdosTernary.Records.UpTo36 ErdosTernary.upTo_36 --expect UpTo:2*3^36`
  gives `LEAN_AUDIT: PASS tier=B`. The axioms are propext, Classical.choice, Quot.sound and
  `CheckerWord2.word2_36_{0..15}._native.native_decide.ax_1_1`.

## Clean build
* ETNative build outputs were deleted before any record build:
  `.lake/build/lib/libErdosTernary_ETNative.so*`, `.lake/build/lib/lean/ETNative.*` and `.lake/build/ir/ETNative.*`.
* ETNative was then rebuilt from source (`lake build`, then `lake build ETNative:shared`). All record shards and
  timings below used that .so.
* No diagnostic or unsound variant was written: the only timing harnesses are scratch files outside the repo that
  call the committed definitions.
* Pitfall found and worth recording: `lake build ETNative` refreshes the .olean but NOT
  `libErdosTernary_ETNative.so`. My first timing ran against a stale .so (without `CheckerWord2`), so
  `checkWord2` ran in the IR interpreter and looked 50x slower.
  * `lake build` of an importing module, or `lake build ETNative:shared`, does rebuild the .so.
  * Standalone `#eval`/`--run` timings must therefore check the .so first, for example with
    `nm -D … | grep CheckerWord2`.

## Timing (this machine, 4 cores, nice 10, LEAN_NUM_THREADS=1, Lean 4.36.0, up to 3 jobs at once, no other load)
* Harness: `lake env lean --load-dynlib=.lake/build/lib/libErdosTernary_ETNative.so --run Tm.lean <k> …`. It times
  `checkWord2 N 0 1` and `checkWord N 0 1` (the whole tree, one shard) with `IO.monoNanosNow`, as native code, the
  same path native_decide uses.
* Unit = node of the g005-R01 counting, `2^(K+1) + 1` units for `N = 2*3^K`.
* K = 24 is the mean of 3 repeats (w2: 1.527, 1.523, 1.528; w: 0.938, 0.942, 0.974). The other rows are single runs.

| N | checkWord2 (s) | ns/unit | checkWord (s) | ns/unit | speedup |
|---|---|---|---|---|---|
| 2*3^24 | 1.526 | 45.5 | 0.952 | 28.4 | 0.62x |
| 2*3^28 | 24.38 | 45.4 | 21.69 | 40.4 | 0.89x |
| 2*3^30 | 97.47 | 45.4 | 132.08 | 61.5 | 1.36x |
| 2*3^32 | 389.7 | 45.4 | 951.8 | 110.8 | 2.44x |
| 2*3^34 | 1572 CPU (8 shard modules: 215, 190, 175, 193, 220, 214, 172, 194 s, lake + import included) | 45.7 | not run | | |

* At small N, `checkWord2` is slower than `checkWord`, because a two-word step costs 13 products against 3.
* At K = 28 the curves cross. From there `checkWord`'s `deep` share grows (4.8x average for 24→28, then 6.1x and 7.2x per two powers), while
  `checkWord2` stays at 4.00x.
* Wall time for `UpTo (2*3^34)`: 05:28:40 to 05:38:46 UTC, about 10 min with 3 shards at a time (two timing jobs
  shared the cores near the end). `UpTo (2*3^36)`: 05:53:35 to 06:31:28 UTC, about 38 min wall with 3 at a time.

## Scaling (HEURISTIC)
* Measured growth per two powers of 3: 4.00 (24→28 is 15.98 over two steps), 4.00 (28→30), 4.00 (30→32), and
  4.03 (32→34 including module overhead), 3.98 (34→36, both sharded record builds).
* Sampled shard (`checkWord2 N 5 512`): 1.14, 4.57, 18.16 and 73.38 s for K = 32, 34, 36 and 38, that is 4.0x per step.
* Sampled shard (`checkWord2 N 5 2048`): K = 38 took 24.44 s and K = 40 took 241.46 s, which is **9.9x, not 4x**.
  * Cause: for `N >= 2^63`, i.e. from K = 40 on (2*3^39 < 2^63 < 2*3^40), `N`, the representative `r` at levels
    >= 40, and the periods `p = 2*3^j` for j >= 39 are GMP numbers. Every `N < r + e.p` and every `r + e.p` then
    allocates. The trit state is still scalar.
  * So the claim "no node needs bignum for N <= 2*3^46" holds for the residue state but not for the
    representative `r`.
* Extrapolation to `2*3^46` (`2^47+1 = 1.41e14` units):
  * At the measured 45.4 ns/unit: 6.4e6 s ≈ 74 CPU-days. This is a lower bound, valid only if `r`/`N` stayed scalar.
  * With the K = 40 penalty (about 2.47x per unit, so about 112 ns/unit), assuming it stays flat for K = 40..46:
    about 1.6e7 s ≈ 180 CPU-days, or about 46 days on 4 cores.
  * The penalty is one sample, a single run of one shard of 2048. Treat it as ±50 %.
* Next hypothesis (not done here: one mechanism per experiment): keep `r` and `N - r` scalar as well. For example,
  carry `r` relative to the shard-level representative as a word offset plus the level, or as two words. Then the
  45 ns/unit carries to K = 46, about 74 CPU-days.

## Risks
* Trust base: unchanged in kind (README "What tier B trusts"). An audit must delete the ETNative outputs and rebuild
  the .so from source. Note the `lake build ETNative` pitfall above: build the importing record module, or
  `ETNative:shared`.
* Overflow to bignum is silent. If a future edit lets a column exceed 2^63, the result stays correct but the gain is
  lost. `mul2_gen` has no bound hypotheses.
* `mulHi` duplicates work from `mulLo`. That costs speed, not correctness.
* All timings were taken on one machine with up to 3 concurrent jobs. The K >= 28 rows are single runs.
