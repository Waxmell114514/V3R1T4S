# Claim g003-C04 (upgrade of milestone M1 to tier A)

Scope, exactly: in the Lean 4 + Mathlib v4.36.0 project campaigns/erdos-ternary/lean, against the frozen
definitions in verify/Statement.lean (copy here):
1. `ErdosTernary.CheckerKernel.checkK_sound : checkK N K = true → ErdosTernary.UpTo N` (all N, K) — tier A.
2. `ErdosTernary.upToK_20 : UpTo (2*3^20)` in lean/ErdosTernary/Records/CheckerKernelUpTo20.lean — tier A:
   kernel evaluation only (`decide +kernel` on ≤30000-node subtrees, assembled by the proved lemmas
   `exploreK_of_children` / `checkK_of_roots`); no native_decide, so it does not trust the Lean compiler.
   (Also `upToK_16` in CheckerKernelUpTo16.lean and `upToK_18` in Records/CheckerKernelUpTo18.lean, tier A.)
UpTo N means: for all n with 8 < n ≤ N, the base-3 expansion of 2^n contains the digit 2.
The large proof files were generated by tools/gen_kernel_upto.py, an untrusted generator; their sha256 are in
generated_files.sha256. Correctness rests only on Lean checking them.

Not claimed: anything new mathematically. 2*3^20 is Vardi's known bound; M1 was already met at tier B
(panel/g002-L01/gate.md). This claim only upgrades M1's evidence to tier A.

How to rerun: `cd campaigns/erdos-ternary/lean && lake build ErdosTernary.Records.CheckerKernelUpTo20`
(about 15 min of kernel time; Records modules are not in the default build), then from campaigns/erdos-ternary:
`python3 verify/lean_audit.py ErdosTernary.Records.CheckerKernelUpTo20 ErdosTernary.upToK_20 --expect UpTo:2*3^20`.
