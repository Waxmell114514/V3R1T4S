# g005-C02: word-size checker state (one mechanism: the hot-loop state stays below 2^63, so no GMP)

Prediction recorded before running (orchestrator): 3-5x per node over the precompiled `checkShard`;
`UpTo (2*3^32)` in <= 1.5 h wall.
Outcome: 8.0-8.4x at N = 2*3^22 and 2*3^24 (prediction exceeded there), falling to 5.6x at 2*3^28
(see "Where the gain goes"). `UpTo (2*3^32)` is LEAN-VERIFIED tier B in about 8.5 min wall (prediction met).

## Change
* `lean/ErdosTernary/Native/ETNative.lean`, new namespace `ErdosTernary.CheckerWord` (Mathlib-free, precompiled, no
  attributes): `mulMod`, `Lv`, `scanT`, `deep`, `scan`, `fast`, `table`, `top`, `wordDepth`, `checkWord`.
  The existing definitions are unchanged.
* The tree is the one `CheckerShard` uses (g003-L01), shard level 10. Changes:
  * The modulus is `M = 3^38 = 1350851717672992089 < 2^63` instead of `3^40`. The state is `v = 2^r % M`, and the
    table stores `g = 2^(2*3^j) % M` split as `gh = g / 3^19`, `gl = g % 3^19`.
  * `mulMod M v gh gl`: `vh = v / 3^19`, `vl = v % 3^19`,
    `s = (vh*gl + vl*gh) % 3^19 * 3^19 + vl*gl`, then `if s < M then s else s - M`. Every product is `< 3^38` and
    every sum is `< 2*3^38 < 2^63`, so all values are scalar `Nat`s in the Lean runtime. `3^19` is a literal
    (`lean_unsigned_to_nat`, a constant divisor in C). `M` is a function argument because the C code rebuilds a
    literal `>= 2^32` from a string on each use (`lean_cstr_to_nat`), as seen in `.lake/build/ir/ETNative.c`.
  * A single-member tail that reaches level 38 is re-seeded once by `deep`: `x = Nat.powMod 2 r (3^76) / 3^38`
    (the only bignum step), then 38 more trits are read (`scanT`). After that, and for multi-member nodes at
    level 38, the fallback is `Checker.explore`.
* Design choice: plain `Nat` values kept small, not `UInt64`. The proof needs only `Nat` algebra
  (`mulMod_gen`), and the generated C uses the inline scalar fast paths of `lean_nat_mul/div/mod`.
  A UInt64 version was not built or measured.
* `lean/ErdosTernary/CheckerWord.lean` (imported by `ErdosTernary.lean`) holds the soundness proofs. It reuses
  `CheckerShard.Good`, `split_class`, `good_of_trit`, `good_of_lt`, `good_single`, `good_of_explore` and
  `trit_of_mod`.
* `Records/UpTo32.lean` + `Records/UpTo32/Shard{0..7}.lean` (not imported by default):
  `checkWord (2*3^32) s 8 = true` by native_decide.

## Theorems
* `CheckerWord.mulMod_eq (v gh gl) (hgl : gl < 1162261467) : mulMod (3^38) v gh gl = v * (gh * 1162261467 + gl) % 3^38`
* `CheckerWord.checkWord_sound {N m : ℕ} (hm : 0 < m) (h : ∀ s < m, checkWord N s m = true) : UpTo N`. Tier A:
  `LEAN_AUDIT: PASS tier=A axioms=['Classical.choice', 'Quot.sound', 'propext']`.
* `upTo_32 : UpTo (2 * 3 ^ 32)`. Tier B: `lean_audit.py ErdosTernary.Records.UpTo32 ErdosTernary.upTo_32
  --expect UpTo:2*3^32` gives `LEAN_AUDIT: PASS tier=B` with axioms propext, Classical.choice, Quot.sound and
  `CheckerWord.word32_{0..7}._native.native_decide.ax_1_1`.

## Where the gain goes (measured)
I ran a diagnostic build with `deep` replaced by a constant `true`. It was unsound, used only for timing and then
reverted, and the .so was rebuilt from source afterwards. It gave 13.5 s at k = 28 (vs 22.7 s) and 53.4 s at
k = 30 (vs 138.6 s). So the once-per-tail `Nat.powMod 2 r (3^76)` (GMP) is 40 % of the time at k = 28 and 61 %
at k = 30. The share grows with k because tails start near level k+1 and reach level 38 more often. Without
`deep`, the word checker grows 3.94x per two powers of 3, the same rate as checkShard (about 4.0x).

## Scaling (HEURISTIC)
* As committed, `checkWord` is efficient only for K <= 37. For K >= 38, multi-member nodes reach level 38 and
  go to `explore` (a bignum `powMod` per node), and the `deep` share keeps rising. Measured growth per two
  powers: 4.2, 4.5, 5.1, 6.1, 7.4 (k = 22 → 32). Do not extrapolate it to 2*3^46.
* With a two-word state (2^r mod 3^76 as two scalar words base 3^38; the products need four 19-trit partial
  products), the table would reach level 75 and `deep` would go away. If such a node costs about 2x the
  no-deep word node, then 2*3^32 takes about 420 s and 2*3^46 about 420 * 3.95^7 ≈ 6.6e6 s ≈ 75 CPU-days.
  Before this change the estimate was 9 CPU-years (g004-C02). M2 still needs an algorithmic change.

## Risks
* Trust base: unchanged in kind (README "What tier B trusts"). The audit must rebuild ETNative from source.
* `mulMod` correctness does not depend on the bounds; only speed does. If `v` or `g` were `>= 3^38`, values would
  only become bignums. The proof covers every input.
* Overflow-to-bignum is silent. A future edit that raises `M` past 2^63/2 would stay correct but would lose the gain.
* Timings were taken on a shared machine (load 2-3). The k >= 26 rows are single runs.
