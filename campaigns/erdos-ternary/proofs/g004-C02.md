# g004-C02: precompiled checker (one mechanism: native code for `native_decide` instead of the IR interpreter)

Prediction recorded before running (orchestrator): >= 10x per node; `UpTo (2*3^30)` in <= 1 hour wall.
Outcome: about 4x per node (prediction MISSED); `UpTo (2*3^30)` LEAN-VERIFIED tier B in 687 s wall (met).

## Change
* New lean_lib `ETNative` (lakefile.toml, `precompileModules = true`), one module
  `lean/ErdosTernary/Native/ETNative.lean`, core imports only (no Mathlib). It holds the executable definitions
  `Checker.explore`, `Checker.check`, `CheckerShard.Lvl/scan/fast/table/top/shardDepth/modExp/checkShard`, moved
  verbatim from Checker.lean and CheckerShard.lean with the same fully qualified names (`ℕ` spelled `Nat`).
  All proofs stay where they were and are unchanged. The file is under lean/ErdosTernary/, so lean_audit.py scans it.
* Lake compiles it to C, links `.lake/build/lib/libErdosTernary_ETNative.so`, and passes that library as a plugin
  (in the `--setup` json) to every `lean` run on a module that imports it. The IR interpreter then calls the
  native symbols for these definitions.
* Why a separate Mathlib-free lib: precompiling a module requires shared libraries for its whole import closure
  (Lake `fetchImportLibs`), i.e. compiling Mathlib to C.
* Elaborated definitions compared with `#print` under `pp.all` before/after: the only differences are
  (a) `^` elaborates via core `instPowNat` instead of Mathlib's `Monoid.toNPow Nat.instMonoid` (definitionally equal;
  all soundness proofs re-check unchanged), (b) `top` reuses the auxiliary matcher `explore.match_1` instead of its
  own `top.match_1` (same matcher).

## Results (LEAN-VERIFIED where marked; times from `time`/Lake output, this machine, nice 10, LEAN_NUM_THREADS=1)
* `CheckerShard.checkShard_sound` tier A, `upTo_26` tier B, `upTo_30 : UpTo (2 * 3 ^ 30)` tier B
  (8 shard modules `Records/UpTo30/Shard{0..7}`, `checkShard (2*3^30) s 8 = true` by native_decide).
* Speed, `checkShard (2*3^22) 0 1` (whole tree), net of 1.3-1.6 s import: interpreter 7.36 s, native 1.79 s (4.1x).
  `2*3^24`: 29.9 s vs 7.88 s (3.8x). `UpTo28` module: 136 s (README: ~8-11 min interpreted, earlier session).
* UpTo30 shards (s): 92, 81, 75, 82, 94, 91, 73, 84; combine 1 s; total 687 s sequential.

## Why not 10x (HEURISTIC)
State values live mod 3^40 > 2^63, so every product `v * g` is a GMP bignum; that runtime work is the same in
the interpreter and in native code. Only the interpretive overhead goes away.

## Scaling (HEURISTIC)
Measured growth 2*3^28 -> 2*3^30: 136 s -> 687 s, i.e. 2.25x per power of 3. Extrapolated: 2*3^36 ~ 1 day,
2*3^40 ~ 26 days, 2*3^46 ~ 9 CPU-years single-thread. M2 needs a different algorithmic mechanism, not only this one.
